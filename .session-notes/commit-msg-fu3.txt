refactor(frontend): type-safe status contract end-to-end (#19 followup #3)

Picks up PR #1 followup #3 — eliminates the string-typed boundary on
`getStatusColor`, adds `paymentCompleted` as the boolean complement of
`interactiveStatus`, and routes every status-only boolean gate through
the typed helpers. The audited sites are explicit per-file permissions
to use raw `=== 'STATUS'` checks where the literal IS the discriminated-
union narrowing site (different JSX per status, or reading `paidAt` /
`paymentTxHash` / `payerPublicKey`).

Helpers
=======

`frontend/lib/utils.ts`:

1.  `getStatusColor` parameter tightened from `string` to
    `InvoiceStatus`. Compile errors will now surface at any caller that
    passes a non-typed status. The single existing caller
    (`InvoiceCard.tsx:22`) passes `invoice.status` which is already
    `InvoiceStatus` via the discriminated union — no runtime change.

2.  `paymentCompleted(status: InvoiceStatus): boolean` added as the
    boolean complement of `interactiveStatus`. JSDoc is explicit about
    the non-usage boundary: do NOT use as a discriminator when reading
    `paidAt` / `paymentTxHash` / `payerPublicKey` (the helper returns
    `boolean`, which loses the discriminated-union narrow).

Tests extended
==============

`frontend/lib/utils.test.ts` (16 tests, was 4):

*  `paymentCompleted` matrix (4): PAID → true; PENDING/EXPIRED/CANCELLED
   → false. Mirrors the existing `interactiveStatus` matrix shape.

*  `getStatusColor` matrix (4): typed-Union → expected className. Acts
   as a static gate anchoring the tightened parameter.

*  `interactiveStatus AND paymentCompleted are mutually exclusive`
   (4): sanity invariant — neither predicate returns true
   simultaneously. Catches drift if either widens (e.g. if
   `interactiveStatus` ever covers PAID). Not a XOR — terminal statuses
   return false from BOTH.

   `paymentCompleted(inv.status)`.

   gates: `interactiveStatus(result.data.status as InvoiceStatus)`
   and `paymentCompleted(result.data.status as InvoiceStatus)`.
   The `as InvoiceStatus` casts on `any`-shaped API data are the
   tactical compromise; the long-term fix is to retype
   `invoiceApi.getById` to return `{ data: Invoice }` (followup).

*  `app/pay/[id]/page.tsx:303` — Download/Email button mount: now
   `paymentCompleted(invoice.status) && (…)`. The handlers' internal
   `as any` casts (lines ~119, ~129) are out-of-scope residuals.

*  `app/invoice/[id]/page.tsx:122, 184` — share button mount and
   View-on-Explorer anchor gate, both PENDING content-rendering
   without PAID-field reads: now `interactiveStatus(invoice.status)`.

*  `app/invoice/[id]/page.tsx:203` — PaymentStatus component mount
   for non-PAID: `!paymentCompleted(invoice.status)`. Safe under the
   tightening because PaymentStatus now takes `InvoiceStatus`;
   reading `invoice.paymentTxHash` on the non-PAID variant is
   `never | undefined` (compiles as `undefined`), compatible with
   `txHash?: string`.

*  `app/invoice/[id]/page.tsx:207` — PaymentReceipt component mount:
   `paymentCompleted(invoice.status)`. PaymentReceipt itself has the
   defensive `if (invoice.status !== 'PAID') return null;` narrow

===============

*  `components/PaymentStatus.tsx:6` — `status` prop from inline union

Sites intentionally kept as raw `=== 'STATUS'`
==============================================

These are content-rendering or narrowing-required sites. Replacing
with a predicate helper would lose the inferred InvoicePaid narrow
and break reads of `paidAt` / `paymentTxHash` / `payerPublicKey`:

*  `pay/[id]/page.tsx:263, 269, 275, 284, 324, 377, 381` — per-status
   content rendering (different JSX/text per status).
*  `pay/[id]/page.tsx:293` — `formatDate(invoice.paidAt)` reads
   `paidAt` (PAID-specific).
*  `invoice/[id]/page.tsx:193` — same: `formatDate(invoice.paidAt)`.
*  `components/PaymentReceipt.tsx:22` —
   `if (invoice.status !== 'PAID') return null;` is the defensive
   InvoicePaid narrow at function top.
*  `lib/export.ts:438, 616, 646, 702, 712` — `isPaid` locals in PDF /
   email template generators, used as ternary discriminators
   accessing PAID-specific fields.
